# Event Collection

Личная коллекция посещенных мероприятий: консольное приложение (ПР1–ПР3), веб-интерфейс на Django с шаблонами (ПР5–ПР6) и база данных SQLite (ПР7).

## Назначение

Event Collection — сервис для ведения личной коллекции посещенных мероприятий: концертов, спектаклей, выставок, фестивалей, спортивных матчей. Пользователь отмечает мероприятия, на которых побывал, ставит им оценки и в любой момент может посмотреть свою историю посещений.

## Используемые технологии

- Python 3;
- Django 5.2 — веб-фреймворк;
- Django Template Language (DTL) — шаблоны страниц;
- SQLite и язык SQL — хранение и обработка данных;
- модуль sqlite3 стандартной библиотеки Python;
- HTML5, CSS3, JavaScript, Bootstrap 5.3;
- JSON — исходные данные проекта (ПР1–ПР6);
- pytest — автоматизированные тесты;
- flake8 — проверка качества кода.

## Целевая аудитория

Люди, которые регулярно посещают культурные, развлекательные и спортивные мероприятия и хотят вести личную историю посещений.

## Предметная область

Досуг и культурно-массовые мероприятия. Мероприятие — событие с названием, категорией и датой проведения. Пользователь добавляет в коллекцию посещения уже состоявшихся мероприятий и оценивает каждое посещение по шкале от 1 до 5.

## База данных

Данные проекта хранятся в базе SQLite `data/event_collection.sqlite`. Таблицы созданы командами из файла `sql/schema.sql`.

### Таблица users — пользователи

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `name` | TEXT | имя пользователя |
| `email` | TEXT | электронная почта |

### Таблица events — мероприятия

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `title` | TEXT | название |
| `title_lower` | TEXT | название в нижнем регистре для поиска |
| `category` | TEXT | категория |
| `date` | TEXT | дата в формате ГГГГ-ММ-ДД |

### Таблица visits — посещения

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `user_id` | INTEGER | внешний ключ на `users.id` |
| `event_id` | INTEGER | внешний ключ на `events.id` |

### Таблица ratings — оценки

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | первичный ключ |
| `visit_id` | INTEGER | внешний ключ на `visits.id` |
| `score` | INTEGER | балл от 1 до 5 |

Связи предметной области:

```text
users.id  ──< visits.user_id
events.id ──< visits.event_id
visits.id ──< ratings.visit_id
```

Поле `title_lower` появилось из-за особенности SQLite: функция `LOWER()` не приводит к нижнему регистру кириллицу, поэтому поиск без учета регистра выполняется по заранее подготовленному полю.

## Работа с базой данных из Python

- `db/database.py` — функция `get_connection()` открывает соединение, включает `PRAGMA foreign_keys = ON` и настраивает `row_factory = sqlite3.Row`, чтобы обращаться к полям результата по именам; функции `fetch_all()` и `fetch_one()` выполняют запрос с параметрами и возвращают строки;
- `db/import_json.py` — создает таблицы по `sql/schema.sql` и переносит данные из JSON-файлов методом `executemany()`; при ошибке выполняется `rollback()`.

Создание базы и перенос данных:

```bash
python -m db.import_json
```

## SQL-запросы проекта

Проверенные запросы хранятся в файле `sql/queries.sql` (16 запросов с комментариями):

- списки объектов: мероприятия, пользователи, категории (`SELECT`, `ORDER BY`, `DISTINCT`);
- фильтрация: поиск по части названия (`LIKE`), выбор категории, прошедшие мероприятия, карточка по номеру (`WHERE`);
- связанные данные: посещения с пользователем, мероприятием и оценкой (`JOIN`, `LEFT JOIN`);
- подсчеты: количество записей и средняя оценка (`COUNT`, `AVG`, `ROUND`);
- группировка: посещения и средние оценки по категориям (`GROUP BY`), категории с числом посещений больше заданного (`HAVING`), самые посещаемые мероприятия (`LIMIT`);
- подзапрос: мероприятия, которых еще нет в коллекции пользователя (`NOT IN`);
- проверка отсутствующих значений: посещения без оценки (`IS NULL`).

Значения всегда передаются параметрами `?`: подстановка пользовательского ввода в текст запроса не используется.

## Веб-интерфейс

| URL | Страница | View-функция | Какой SQL выполняется |
|---|---|---|---|
| `/` | главная | `homepage.views.index()` | — |
| `/events/` | список мероприятий | `events.views.events()` | `SELECT` с сортировкой по дате |
| `/events/search/` | поиск мероприятий | `events.views.event_search()` | `WHERE title_lower LIKE ?` и категория |
| `/events/<int:event_id>/` | карточка мероприятия | `events.views.event_detail()` | `LEFT JOIN` + `COUNT` + `AVG` + `GROUP BY` |
| `/visits/` | список посещений | `visits.views.visits()` | `JOIN` трех таблиц + `LEFT JOIN` оценок |
| `/visits/statistics/` | статистика | `visits.views.statistics()` | `COUNT`, `AVG`, `GROUP BY`, `HAVING` |
| `/visits/<int:visit_id>/` | карточка посещения | `visits.views.visit_detail()` | `JOIN` + `WHERE visits.id = ?` |

Если объекта с указанным номером нет, страница возвращается с кодом 404.

## Шаблоны Django

Общая структура страниц — в `templates/base.html`; дочерние шаблоны наследуют его через `{% extends %}` и заполняют блоки `title` и `content`. Повторяющиеся фрагменты подключаются тегом `{% include %}`: навигация, карточка мероприятия, оценка посещения. Ссылки формируются именованными маршрутами `{% url %}`, данные приходят из представлений через контекст.

## Статические файлы

`homepage/static/homepage/`: собственный `css/style.css`, скрипт `js/main.js` (текущий год в подвале) и логотип `img/logo.png`. Подключаются в базовом шаблоне через `{% load static %}` и `{% static %}`.

## Структура проекта

- manage.py — запуск команд Django;
- eventcollection/ — настройки проекта и корневые маршруты;
- templates/ — базовый шаблон и навигация;
- homepage/, events/, visits/ — Django-приложения: представления, маршруты, шаблоны, статика;
- db/ — работа с базой данных: `database.py`, `import_json.py`;
- sql/ — `schema.sql` (создание таблиц) и `queries.sql` (запросы проекта);
- data/ — JSON-файлы ПР1–ПР6 и файл базы `event_collection.sqlite`;
- models/ — классы предметной области `User`, `Event`, `Visit`, `Rating` (ПР3);
- storage.py, utils.py, main.py — консольная версия приложения;
- tests/ — автоматизированные тесты.

## Хранение данных: два слоя

JSON-файлы ПР1–ПР6 сохранены: с ними работают консольное приложение и тесты. Веб-страницы после ПР7 получают данные из SQLite. Исходные JSON остаются источником для переноса данных в базу.
